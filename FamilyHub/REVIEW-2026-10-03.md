# FamilyHubCore correctness review (2026-10-03)

Scope: `Packages/FamilyHubCore` (Engagement, Models, OpenerGenerator, Store, SuggestionEngine and both test files), plus how `App/*.swift` and `Widget/FamilyHubWidget.swift` call the core.

> **Status: nothing here has been compiled or run.** This PC has no Swift toolchain. Every fix and test was checked by hand-tracing the code. CI (`.github/workflows/ios.yml`) runs `swift test` on the next push that touches `FamilyHub/`, so that push is the first real check.

Line numbers refer to the files after this review's changes.

## Findings

| # | Where | Severity | What | Status |
|---|-------|----------|------|--------|
| 1 | `Store.swift:128` `load()` | **High** (data loss) | Any read or decode failure returned an empty `AppData()`. The app's next `update` (or the widget's ✓ button) then saved that over the real file, so every person, the whole log, all badges and preferences were gone with no copy left. One bad element (for example an unknown `ReachOut.Kind` after a downgrade, or a malformed person) fails the entire decode. | **Fixed (partly).** Before returning empty data, `load()` now copies the unreadable file to `familyhub.unreadable.json`. Only the first bad file is kept and it is never overwritten. A missing file still means a fresh install. The real fix (don't save after a failed load, and tell the user) is an app change: see the owner decision below. |
| 2 | `Engagement.swift:198` `streak` (day loop) | **Medium** (wrong streak in some time zones) | The loop adds one day at a time to a start-of-day. Where DST starts at midnight (Chile, also Paraguay, Cuba and Lebanon), that day starts at 01:00, and every later step stays at 01:00. From then on no day matches the start-of-day keys, so every day looks missed: the streak resets and freezes are burned. In Santiago (2026-09-06), a 10-day streak came out as 0. | **Fixed.** Each step is re-anchored with `startOfDay(for:)`. Test: `testStreakSurvivesAMidnightDSTChange`. |
| 3 | `Engagement.swift:254` `activity` | Low | Same root cause. On the DST-start day itself (today starts at 01:00), earlier days are looked up at 01:00 and the weekly chart shows 0 for them. | **Fixed.** Test: `testActivityOnTheDayDSTStartsAtOneAM`. |
| 4 | `Engagement.swift:294` `daysBetween`, `SuggestionEngine.swift:23` | Low–Medium (plausible) | The day difference was measured from start-of-day to start-of-day. When one day starts at 01:00, the next day's start is only 23 h later, and Foundation can report 0 days. That gives a wrong "days since", wrong urgency, wrong `score` kind and a wrong `personStreak`. | **Fixed.** The difference is now measured noon to noon, and `SuggestionEngine` uses the same helper. Test: `testDaysSinceAcrossAMidnightDSTChange`. Note: whether the old code really fails depends on Foundation's day-difference behaviour, which I couldn't run. The test passes either way after the fix. |
| 5 | `Engagement.swift:242` `level(xp:)` | Low | Negative XP (only possible from a corrupt or hand-edited log) fell through to the "past max level" branch. `level(xp: -10)` returned level 7 "Hall of Famer". | **Fixed.** XP is clamped to 0 or more. Test: `testNegativeXPIsLevelOne`. |
| 6 | `Engagement.swift:136` `StreakStatus.goalMetToday` | Cosmetic | Mis-indented. | **Fixed.** |
| 7 | `Engagement.swift:281` `reminder(for:)` | Medium (product) | `guard let top = suggestions.first else { return nil }` runs before the at-risk check. If your streak is at risk but nobody is due, you get no streak reminder today, and the app reschedules a generic one for tomorrow, after the streak has already broken. | Not fixed: needs the owner's decision (wording). |
| 8 | `Engagement.swift:193` `score` | Low (product) | The reconnect check (`days >= 30`) runs before the on-time check. Anyone with a 30, 60 or 90-day cadence always scores "reconnect" (+25 and the Reconnector badge) even when on time. | Not fixed: owner decision. |
| 9 | `Engagement.swift:198` `streak` / `Preferences.dailyGoal` | Low (product) | The streak is recomputed from the whole history with today's goal. Raising the daily goal from 1 to 2 wipes your current and longest streak, including past days. Badges you already earned are kept. | Not fixed: owner decision. A fix would mean storing the goal per day. |
| 10 | `Engagement.swift:276` `earnedBadges` | Low | `data.suggestions(now:)` ignores the `calendar` argument and uses `Calendar.current`, so the "All caught up" check can disagree with the rest of the badge maths in tests or other time zones. Snoozing everyone also earns "All caught up". | Not fixed (no visible user impact; a test would depend on the Mac's time zone). |
| 11 | `Store.swift:46-53` decoding | Low (future risk) | `AppData` tolerates missing keys, but `Person`, `ReachOut`, `Opener`, `LifeContext` and `Preferences` use synthesized `Codable`. Adding a non-optional field to any of them later makes older files undecodable (see #1). | Not fixed. Rule for future changes: new stored fields must be optional or get a tolerant `init(from:)`. |
| 12 | `App/AppModel.swift:55` `update`, `Widget/FamilyHubWidget.swift:102` `MarkTextedIntent` | Low | The widget's ✓ writes the file directly. If the app is still alive in the background and saves its in-memory copy (for example when an opener refresh finishes) before `reload()` runs, the ✓ is lost. | **Fixed (2026-10-06).** New `Store.update(_:)` does load → change → save under the store's lock and returns the saved data. `AppModel.update` and the widget's `MarkTextedIntent` both use it, so each change is applied to the latest file instead of an in-memory copy. Still not coordinated across processes (no `NSFileCoordinator`): the race window is now one read + write instead of the whole app session. One gap remains: `AppModel.upsert` replaces the whole `Person` from the edit sheet, so saving an edit started before a widget ✓ still puts back that person's old `lastContacted` (the log entry and points are kept). If the file can't be decoded, `update` throws `Store.UnreadableFileError` and saves nothing (the widget's ✓ then fails instead of replacing the file with near-empty data; the app falls back to saving its own copy, as before). Tests: `testUpdateKeepsAWriteFromAnotherStoreOnTheSameFile`, `testUpdateReturnsWhatItSaved`, `testUpdateClosureCanHandBackAResult`, `testUpdateRefusesToReplaceAnUnreadableFile`. |
| 13 | `Engagement.swift:250` `level(xp:)` | Info | `floor + 700` overflows (crash) when XP is within 700 of `Int.max`. Unreachable in practice. | Not fixed. |
| 14 | `OpenerGenerator.swift:134` `userPrompt` | Info | "last texted: N days ago" uses a raw 24 h difference with `Calendar.current`, not calendar days, so it can be 1 lower than the app shows (and it says "1 days"). This only affects the prompt. | Not fixed. |
| 15 | `Widget/FamilyHubWidget.swift:56` | Info | Photos are loaded for the people on top *now*, but later timeline entries (next midnights) can rank different people, who then show initials until the next reload. | Not fixed. |
| 16 | `SuggestionEngine.swift:53` `isFresh` | Info | An opener with a future `createdAt` (clock change) stays "fresh" until the clock catches up. | Not fixed. |

Checked and found correct: the freeze cap at 2, freezes only spent on past days while a streak is running, per-person once-a-day points, badges awarded once, the suggestion order (urgency, then favorite, then score, then name), the urgency thresholds, snooze filtering, the fallback opener seed (non-negative, stable), request privacy (first names only, no phones), and refusal handling. In the app and widget I found no force-unwraps on user data. The remaining `!`s are on constant URLs, `Calendar.date(byAdding:)` and `levelTitles.last!`.

## Tests added

`EngagementTests.swift`
- `testFreezesCapAtTwo`: 21 straight days bank 2 freezes, not 3.
- `testTwoBankedFreezesSaveTwoMissedDaysAndTheThirdResets`: two missed days are covered (current 23, frozen days -3 and -2). A third missed day resets (current 1, longest 21).
- `testStreakSurvivesAMidnightDSTChange` (regression for #2): Santiago, Sept 1–10 2026 gives current 10 and 1 freeze.
- `testActivityOnTheDayDSTStartsAtOneAM` (regression for #3): gives `[0, 1, 1]`.
- `testLevelBoundariesAndLargeXP`: 49 XP is level 1, 50 is level 2 (50→125), 3199 is level 10 (1 to next), and 1,000,000 is level 1435 (floor 1,000,000, next 1,000,700).
- `testNegativeXPIsLevelOne` (regression for #5).

`FamilyHubCoreTests.swift`
- `testFavoriteNeverOutranksAHigherUrgency`
- `testEqualScoresSortByNameIgnoringCase`
- `testUrgencyThresholds`: the 0.75, 1.0 and 1.5 boundaries.
- `testFutureLastContactedCountsAsToday`
- `testDaysSinceAcrossAMidnightDSTChange` (regression for #4)
- `testUnreadableFileIsBackedUpBeforeASaveCanOverwriteIt` (regression for #1)
- `testUpdateKeepsAWriteFromAnotherStoreOnTheSameFile` (regression for #12): a second `Store` on the same file (the widget) logs a reach-out, then the first one updates from its stale copy. The reach-out is kept.
- `testUpdateReturnsWhatItSaved`: the returned data equals what `load()` reads back.
- `testUpdateClosureCanHandBackAResult`: `markContacted`'s result can be captured from inside the closure.
- `PersonMergeTests` (follow-up to #12): saving the edit sheet merges only the fields you changed (`Person.applyingEdits`), so a widget ✓ made while the sheet was open isn't undone.

The DST tests depend on the Mac's time-zone data (Chile starting DST at 00:00 on 2026-09-06). I confirmed that date against Windows' time-zone data.
